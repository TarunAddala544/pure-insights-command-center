### What each worksheet asserts

* **97 — attribution integrity.** The credit-bucket identity (`attributed + unattributed_idle + excluded_negative = metered_total`, gap = 0); a per-report recount computed directly from `RAW_REPORT_SNAPSHOTS`, independent of the cleaning pipeline, compared against `REPORT_CREDIT_ATTRIBUTION` for all 100 reports (0 differ); fleet totals; that `RPT_223` is the top-cost report and its unit cost is 4.539; that no report has a NULL unit cost; and that all 6 rows of `RECONCILIATION_CHECKS` passed.
* **98 — spot check against a hand-computed sheet.** Re-derives the 10 items in `spot_check_sheet.csv` two ways: straight from the raw table exactly as the sheet's `how_to_compute` column describes (credit price typed in literally, on purpose), and from the suite's own tables and views. PASS requires every non-NULL value to match the sheet.
* **99 — generated reconciliation against pandas.** Thirteen headline metrics with their expected values baked in from `validation/verify.py`, so a drift in either engine fails visibly.

### Reading the 98 result

One row — *"Whole file: rows with latency exactly 15.0"* — has an empty `PIPELINE_VALUE`. That is expected, not a gap: `LATENCY_SEVERITY` only contains rows that breach the threshold, and 15.0 does not breach a strictly-greater-than-15 rule. The raw-SQL value (7) matches the sheet, so the check passes on the values that exist. This is the boundary case the alert engine is pinned on in `backend/test/domain.test.js` (14.9 / 15.0 / 15.1).

## Why three engines

Each one can be wrong in a way the others are not. A bug in `clean.js` would propagate into any check written against the same ingestion. pandas reads the CSV independently; Snowflake and DuckDB execute the same SQL text on different engines. Agreement across all three is what makes the numbers in `docs/DATA_QUALITY_REPORT.md` reportable rather than merely self-consistent.
